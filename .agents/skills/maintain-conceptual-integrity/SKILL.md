# 认知一致性与维护成本

首要目标是长期可维护性：让维护者用少量连贯的概念理解系统，修改一项规则时自然知道应该改哪里，新增功能时能够沿已有结构继续生长。

做法是让同一种事情只有一条路。复杂度用于在源头把路合成一条，不要绕开现有结构做补偿。

结合当前仓库的 `AGENTS.md`、`CONTRIBUTING.md`，以及 `docs/BackendStructure.md`、`docs/FrontendGuide.md`、`docs/FrontendHostContract.md` 等相关文档应用以下判断。

## 从整体需求推导结构

先理解用户希望完成的事情，再沿实际流程追踪数据、状态和行为。找出几个入口实际上共享的需求，以及当前复杂度从哪里产生。源码、实际使用和可复现行为是判断依据。

思考方案时，把现有实现（包括相关文档）也作为可以改变的设计选择。若当前问题来自职责分散、状态重复或数据路径别扭，就重新整理这段结构，让问题在共同机制中得到解决。

## 让同一种事情遵循同一套规则

把共同语义放在一处实现，各入口提供自身的数据和上下文。功能模块表达实例含义，共享机制承担共同行为。状态有明确来源，其他部分围绕它工作。

例如，Shell 与文本工具都在操作工作区，文件是否适合自动提交，应由共同的提交规则决定（`docs/Agent/Workspace.md`）。接入新工具时，让它进入已有文件与提交路径，维护者就只需理解一套工作区概念。前端控件同理：功能提供名称、内容和业务状态，浏览器与共同控件负责共同行为（`docs/FrontendAccessibility.md`）。

入口或写入者之间出现分歧时，修改它们，让它们遵循同一协议；不在下游用观察、同步或补偿去调和分歧。例如 API 修改数值约束后，由它发送与用户操作相同的 `input`，共同实现随之同步数字框，不另挂观察器。

用这种思路检查新增的入口或能力：

- 它是上游兼容行为还是 TauriTavern 新能力？前者保持 `/api/*`、资源路径、stream 与事件语义，后者通过 `window.__TAURITAVERN__.api.*` 暴露（BackendStructure §5、§10）。
- 它能否进入已有的共同路径？是否引入了第二个事实来源、第二条链路，或为某个扩展、provider、入口另写分支？按平台适配属于真实差异。
- 发现的问题能否在源头修正，让所有入口一起受益？若每个入口都需要自己的补丁，或者需要在下游补偿，应继续寻找真正共同的职责。

共同机制的边界由语义决定。把含义相同的规则收敛起来，把真实差异清楚表达出来，形成可以持续演进的结构。

## 用重构换取后续开发的简单

当重构能够减少重复链路、隐含知识和反复补偿时，就直接调整相关结构和规划。可以接受一次较大的改动，换取以后每次修改都更直接。评价的是整个系统的理解和修改成本。动手前与维护者对齐会改变行为和责任的决定，对齐后直接重构到位。

先把共同机制做完整，再按功能接入。迁移全部实际调用者，同步删除被替代的实现和旁路，更新原有说明，让新结构成为正常开发路径；只在旧结构外再加一层不算完成。分块实施应当逐步完成同一套架构。

兼容的硬边界是已被使用的生态契约：上游前端、扩展、脚本和角色卡实际依赖的入口、DOM 约定与时序。确认具体消费者，把这些入口保留为转入共同机制的薄入口。契约之外都是可以重构的实现（FrontendHostContract §1），来自上游的代码也不例外；上游的不一致写法和旧缺陷不是契约，应在源头改正。

模块通过清楚的接口隐藏内部细节。维护者理解当前功能和它依赖的少量契约，就应足以完成工作；对扩展作者而言，这份契约就是 FrontendHostContract 与 `docs/API/`。好的抽象让调用者少想几件事，也让一次规则变化集中在合适的位置。

## 让复杂度与当前问题相称

优先复用已有机制、标准库和平台能力，选择能够完整解决现实需求的简单方案。KISS 看概念、依赖和隐含知识；60/95 鼓励把精力投入主要使用场景。

不为尚未出现的问题预先建机制，也不在各层重复防御；问题真正出现时，在它的源头修正。可恢复的小问题不阻塞主流程。解决真实问题所需的机制，弄清职责后照样保留，例如工作区编辑同时需要 CAS 与锁，二者守住不同的不变式。

发现问题或评审指出漏洞时，先看能否通过推广已有规则、删除造成分歧的条件或特判来解决，再考虑新增规则。逐条追加的特例会叠加复杂度；一条推广后的规则常常能同时消解多处问题。

错误在负责的边界清楚表达，失败路径保持直接。性能优先从减少重复计算和数据搬运改善；进一步的复杂度由实际问题支撑。

取舍时看长期净收益。必要的共同机制值得建设，一次重构也可以比不断追加小修补更经济。原则服务于判断，新的事实出现后，设计可以随之改变。

## 让代码之外的接口也容易理解

名称、工具参数、返回结果和文档使用一致的概念，并沿用使用者已熟悉的约定。面向用户与 Agent 的语言说明能力、结果和下一步，让内部实现细节留在合适的位置。文字简洁明了、分工明确、中正平和。

测试验证有价值的行为与不变式，随实现收敛重复和失效内容。文档保留总纲、核心契约和重要理由，让读者按需进入细节。代码、测试和文档共同承担维护成本，应当一起整理。

收尾时逐个入口核对它是否已进入共同机制，并问：维护者需要理解的路径是否少了一条？再用下一次开发检验这次设计：维护者是否更容易理解规则、找到修改位置，并沿同一条清楚的路径扩展功能？
